## 概念一：从源码到程序

### 1. 五个阶段与产物

日常说“编译”常把整条构建流水线都包进去；排错时要分开：

| 阶段 | 主要输入 | 主要输出 | 今天的观察方法 | 常见失败 |
|---|---|---|---|---|
| 预处理 | `.cpp`、被包含的 `.hpp`、宏 | 展开的源文本，C++ 常记作 `.ii` | `c++ -E main.cpp` | 头文件找不到、条件宏错误 |
| 编译 | 一个预处理后的翻译单元 | 汇编文本或中间表示 | `c++ -S main.cpp` | 类型、语法、不可见声明错误 |
| 汇编 | 汇编文本 | 对象文件 `.o` | `c++ -c main.cpp -o main.o` | 目标平台/汇编层问题 |
| 链接 | 多个 `.o` 与库 | 可执行文件或库 | `c++ main.o camera.o -o camera_app` | 未定义符号、重复符号、库顺序/架构不匹配 |
| 运行 | 可执行文件与运行时输入 | 输出、文件、退出码 | `./camera_app` | 异常、错误结果、资源/数据问题 |

`c++` 是驱动程序：它根据参数决定执行到哪一步。`-c` 表示“编译并汇编，但不要链接”。因此：

```bash
c++ -c main.cpp -o main.o
```

只证明 `main.cpp` 这个翻译单元能生成对象代码；它不证明 `Camera::project` 的定义最终能被找到。

参考：[Clang Command Guide](https://clang.llvm.org/docs/CommandGuide/clang.html)只看阶段与 `-c/-S/-E` 的说明，8 分钟；看完能把错误归到阶段，而不是把所有错误都叫“编译失败”。

### 2. 翻译单元不是文件名的简单同义词

预处理器把 `#include "camera.hpp"` 的内容插入当前 `.cpp`。一个 `.cpp` 经预处理后的整体才是一个翻译单元。今天有两个翻译单元：

```text
TU 1 = main.cpp + camera.hpp + 标准库头声明
TU 2 = camera.cpp + camera.hpp + 标准库头声明
```

编译器分别检查它们，彼此不“记得”另一个文件的实现。`main.cpp` 只需从头文件知道构造函数和 `project` 的声明就能生成调用；链接器稍后才把调用连接到 `camera.o` 里的定义。

参考：[LearnCpp：Programs with multiple code files](https://www.learncpp.com/cpp-tutorial/programs-with-multiple-code-files/)只看“compiler compiles each file individually”和 linker error 段，8 分钟；看完能解释为何编译顺序不应影响正确程序。

### 3. 声明、定义、头文件与 ODR

声明告诉编译器名字和类型：

```cpp
class Camera {
public:
    Camera(double fx_px, double fy_px, double cx_px, double cy_px);
    Pixel project(const Point3& point_camera_m) const;
};
```

定义提供函数体：

```cpp
Pixel Camera::project(const Point3& point_camera_m) const {
    return {/* ... */};
}
```

今天的规则：

- `camera.hpp` 放类型定义与成员函数声明，用 `#pragma once` 防止同一翻译单元重复包含。
- `camera.cpp` 首先包含配对头文件，再放非内联成员函数定义。
- `main.cpp` 包含接口并调用；不要 `#include "camera.cpp"`。
- 每个普通非内联函数在整个程序中需要一个定义；零个会出现未定义符号，多个会违反 one-definition rule 并常产生 duplicate symbol。

参考：[LearnCpp：Header files](https://www.learncpp.com/cpp-tutorial/header-files/)只看 declaration/definition、paired header、ODR 与 “Do not include `.cpp`”，10 分钟；看完能把接口变化集中在头文件，并让 `.cpp` 作为独立编译输入。

### 4. 对象文件和库

对象文件含机器码、符号表和仍待解析的重定位信息，但通常不能独立运行。库是可复用对象代码的集合：

- 静态库在链接时把需要的代码并入最终程序；
- 动态/共享库在装载或运行时由系统解析；
- 今天不创建库，只直接链接两个 `.o`，为 Day 019 的 build target 做准备。

“头文件”和“库”不是一回事：头文件主要给编译器看声明，库/对象文件给链接器提供实现。仅安装头文件可能编译通过但链接失败；仅有库而没有正确声明则编译阶段就无法正确调用。

参考：[LearnCpp：compiler, linker, libraries](https://www.learncpp.com/cpp-tutorial/introduction-to-the-compiler-linker-and-libraries/)只看 compiler/linker/library 三幅图，6 分钟；看完能回答“为什么头文件不会自动把 `camera.cpp` 链进程序”。

## 概念三：三分类交叉熵与负对数似然

### 1. 随机变量、shape、单位

设模型对一个样本输出：

```text
z:(B,C) = [[2.0, 1.0, 0.1]], B=1, C=3
y:(B,)  = [0]
```

- `z` 是 logits：任意实数、无量纲，不是概率。
- `y=0` 是真实类别索引，不是连续数值 0。
- softmax 后 `q:(1,3)` 是条件分布 `q(c|x)`，每行非负且和为 1。
- 使用自然对数时损失单位为 `nat/example`；若用 `log₂`，单位为 `bit/example`。
- PyTorch 默认 `reduction='mean'`，今天只有一个样本，所以均值等于该样本损失。

### 2. softmax 手算

直接计算 `e^z` 可能溢出，先减去最大 logit `m=max(z)=2`：

```text
q_c = exp(z_c-m) / Σ_j exp(z_j-m)

exp(z-m) = [1, exp(-1), exp(-1.9)]
         ≈ [1, 0.367879, 0.149569]
sum      ≈ 1.517448
q        ≈ [0.659001, 0.242433, 0.098566]
```

减去同一个常数不改变 softmax。它只是数值稳定技巧，不改变类别排序或概率。

### 3. 一般交叉熵、one-hot 特例和 NLL

对真实分布 `p` 与模型分布 `q`：

```text
H(p,q) = -Σ_c p_c ln q_c
```

单个硬标签 `y=0` 可写为 one-hot `p=[1,0,0]`：

```text
H(p,q) = -[1*ln q_0 + 0*ln q_1 + 0*ln q_2]
       = -ln q_0
       = -ln(0.659001)
       = 0.417030 nat/example
```

若把 `q_y` 看成模型给已观察标签的似然，最大化 `ln q_y` 等价于最小化负对数似然 `-ln q_y`。所以硬标签分类中，softmax cross-entropy 与 categorical NLL 数值相同。

但词义仍要说清：

- 交叉熵是两个分布的期望编码代价；
- NLL 是给定观测标签的负对数似然；
- one-hot 经验标签使两者在这个训练目标上相遇；
- 软标签/label smoothing 时公式仍是 `-Σp_c ln q_c`，不再只取一个 `q_y`。

参考：[Deep Learning Book Ch.3](https://www.deeplearningbook.org/contents/prob.html)只看 cross-entropy、KL divergence 和最大似然联系，12 分钟；看完能说明低交叉熵要求把较高概率给真实结果，但不是因果证明。

### 4. 为什么还要报 accuracy 与 Brier

今天的正确类也是最大 logit，因此 accuracy 为 `1`。但 accuracy 只看 argmax，无法区分 `q_y=0.34` 与 `q_y=0.99`。NLL 对把真实类概率压到接近 0 的错误惩罚很大。multiclass Brier 为：

```text
Brier = Σ_c (q_c - 1[c=y])²
```

它也是概率质量误差，范围在 `[0,2]`（本页采用按类别求和、未除以 `C` 的定义）。三个指标回答不同问题：

| 指标 | 回答 | 今天不能推出 |
|---|---|---|
| accuracy | argmax 类别是否正确 | 概率是否可信 |
| NLL/交叉熵 | 给观测标签的概率代价 | 已校准、鲁棒、因果 |
| Brier | 整个概率向量距 one-hot 多远 | 真实部署分布表现 |

校准要求在许多样本上比较置信度与经验正确率；需要温度缩放时，参数只能在验证集拟合。今天只有一个固定样本，所以不计算 ECE，也不声称“模型已校准”。

参考：[PyTorch CrossEntropyLoss](https://docs.pytorch.org/docs/stable/generated/torch.nn.CrossEntropyLoss.html)只看 class-index 输入、reduction 与 LogSoftmax+NLLLoss 等价，10 分钟；看完能解释为何传入原始 logits，而不是先 softmax 后再当 logits。

## 跨线整合：单因素扫描

固定错误类 logits 为 `0,0`，只改变真实类 logit `a∈{-2,0,2,4}`：

```text
z(a)=[a,0,0]
q_y(a)=exp(a)/(exp(a)+2)
NLL(a)=-ln q_y(a)=ln(exp(a)+2)-a
```

预测趋势：`a` 增大时 `q_y` 增大、NLL 下降。`loss_scan.csv` 应有四行。这里“只改变一个参数”让因果归因局限在这个数学函数内部；它不证明真实训练系统中提高某个 logit 的方法有效或安全。

参考：[`verify_cross_entropy.py`](../materials/day018/verify_cross_entropy.py)只看 `loss_scan` 与 CSV 写出，4 分钟；[Deep Learning Book Ch.3](https://www.deeplearningbook.org/contents/prob.html)回看 negative log-likelihood，3 分钟；看完能解释单调趋势和固定条件。

## 常见错误与报错处理

### 1. `fatal error: camera.hpp file not found`

确认从仓库根目录执行，且 `camera.cpp/main.cpp` 与头文件同目录。若从其他目录构建，显式使用 `-I materials/day018`。参考：[LearnCpp Header files](https://www.learncpp.com/cpp-tutorial/header-files/)只看 quotes 与 angle brackets，3 分钟；看完能用双引号包含本项目头文件。

### 2. `undefined symbols` / `undefined reference`

先看链接命令是否含 `camera.o`，再看声明与定义的名称、命名空间、参数和 `const` 是否完全一致。`project(...) const` 与无 `const` 是不同符号。不要通过 `#include "camera.cpp"` 修复。

### 3. `duplicate symbol`

检查是否把普通函数定义放进头文件、重复链接同一对象文件，或同时 include `.cpp` 又单独编译它。参考：[LearnCpp Header files 的 ODR 段](https://www.learncpp.com/cpp-tutorial/header-files/)只看 multiple definitions，4 分钟；看完能保持普通定义唯一。

### 4. `ModuleNotFoundError: torch`

先运行 `python3 -c 'import sys; print(sys.executable)'` 确认解释器，再使用本机已有的 `conda run -n pyt python`。若该环境不存在，切换到你已有的 PyTorch 环境；今天不在计时内安装大包，记录阻塞并完成公式手算和 C++ 部分。参考：[PyTorch Get Started](https://pytorch.org/get-started/locally/)只看平台/包管理器选择，5 分钟；看完能理解安装命令依赖当前操作系统与环境。

### 5. 手算与 PyTorch 差很多

检查：是否把 logits 当概率直接取对数；target 是否为类索引 0；是否错误地先 softmax 又把概率传给 `cross_entropy`；是否使用同一对数底；是否比较相同 reduction。PyTorch 返回自然对数单位。

### 6. accuracy 为 1，于是写“模型可靠”

删除这个结论。单样本只说明 argmax 正确；没有分布外测试、分组表现、校准曲线、鲁棒性或失败案例。今天只能报告固定样本的三项数值与脚本一致性。

1. `#include` 只是把头文件文本放进当前翻译单元，提供类型/声明；编译器不会因此寻找并编译同名 `.cpp`。`camera.cpp` 必须作为独立输入生成 `camera.o`。

3. `-c` 在对象文件后停止，不链接。`c++ main.o camera.o -o camera_app` 产生可执行文件。

6. accuracy 忽略概率幅度；NLL 强烈关注真实类概率但单个均值会掩盖分组/尾部失败；Brier 看整个向量的平方概率误差但仍不能单点证明校准或部署可靠。三者都不能证明因果。
7. `p_true=exp(a)/(exp(a)+2)` 随 `a` 上升，NLL `=-ln p_true` 下降；控制条件是另外两类 logits、target、softmax 和 reduction 不变。
